# 测试能力路线

> 版本：v2.0
> 定位：说明当前具备哪些测试能力、缺哪些、下一步按什么顺序补。
> 与[架构设计](Architecture.md)的分工：那边写「现在是什么」，这边写「还差什么、为什么这样排」。
>
> 关联文档：[架构设计](Architecture.md) · [模式设计](Mode-System-Design.md)

---

## 一、先说清楚现状

当前系统是一个**Agent 优先**的测试工具：模型在循环里现场调用工具（查接口、发请求、评估断言、
写文件），产物以 Markdown 与 JSON 落在空间目录里，执行过程记在 `agent_run` / `agent_tool_call`。

它**不是**一个用例管理平台：没有用例表、没有批量执行器、没有可版本化的测试资产。
这个差别决定了下面的能力地图长什么样。

---

## 二、能力分层

分层不是为了好看，是为了让依赖方向明确：上层可以调用下层，下层不知道上层的存在。

```
L4  对话层（已实现）
    自然语言 → 工具调用。模式（agent/ask/plan）决定这层能用哪些工具

L3  生成层（部分实现）
    OpenAPI / 文档 → 测试思路、断言规则。产物是文件，不是数据库行

L2  执行引擎（未实现）
    变量注入 → HTTP → 断言 → 结果归档。确定性代码，不含 LLM

L1  测试资产层（未实现）
    用例作为可版本化、可编辑、可 diff 的一等公民

L0  规格摄入层（已实现）
    OpenAPI → space / endpoint / environment
```

| 层 | 状态 | 已有 | 缺失 |
|---|---|---|---|
| L0 规格摄入 | 已实现 | `OpenAPIParser`（JSON / YAML，3.0.x 与 3.1.x）、接口落库、环境管理、生产环境标记 | 部分导入（只导入选定接口或 tag） |
| L1 测试资产 | 未实现 | `testcases/` 目录下的 Markdown 文件 | 用例表、用例编辑、版本、去重、diff |
| L2 执行引擎 | 未实现 | 断言引擎（11 个运算符）与 JSONPath 提取，已作为工具暴露 | 批量执行器、连接复用、变量系统、错误分类、可重复执行 |
| L3 生成层 | 部分实现 | 模型按技能方法论现场生成用例与断言，写入文件 | 结构化输出约束、生成去重、断言分层与漂移防护 |
| L4 对话层 | 已实现 | 手写 ReAct、模式白名单、SSE 六事件、执行记录、跨会话记忆、知识库 | 审批流、计划结构化、事件重放、服务端授权 |

这张表最重要的一行是 L2「未实现」。断言引擎有能力、HTTP 工具能发请求、模型能编排顺序，
但**没有一层确定性的执行器**把「读用例 → 注入变量 → 发请求 → 断言 → 归档」固化下来。
所以同样的指令跑两次，产物可能不同——这在探索阶段是可接受的，在回归阶段不可接受。

## 三、为什么先做了 L4 而不是 L2

重构时的判断是：先把「模型能安全地操作这个系统」做扎实，再考虑把操作固化成引擎。
理由有三条：

1. **安全边界必须先有**。文件沙箱、生产环境闸门、模式白名单都是 L4 的组成部分，
   没有它们，L2 一旦接上就是一个能对生产环境随意发请求的批量执行器。
2. **L2 的输入取决于 L1**。没有用例资产，执行器只能执行「模型当场生成的用例」，
   这仍然不是可重复的回归。
3. **探索期的价值在探索**。真实使用中先要回答「这批接口该怎么测」，而不是「怎么把已写好的用例跑 1000 遍」。

代价是清楚的：现在能做探索性测试，不能做稳定回归。这是有意识的取舍，不是能力缺失。

## 四、缺口清单

按「补齐后立刻能解决什么问题」排序，不按实现难度排序。

### 4.1 测试资产层（L1）

- 用例没有唯一标识。同一接口的两条相似用例无法判断是「重复」还是「变体」。
- 用例存在 `testcases/*.md` 里，模型改一次就覆盖一次，没有历史。
- 无法回答「改了接口后，哪几条用例受影响」。

### 4.2 执行引擎（L2）

- 没有批量执行入口。要跑 30 个接口，只能让模型在循环里逐个发，受步数上限与 token 成本约束。
- 没有连接复用。每次 `send_request` 都是独立请求，没有 run 级的连接池。
- 没有变量系统。登录拿 token → 后续接口带 token 这类链路依赖模型自己记住，而不是跑器注入。
- 没有错误分类。当前只有 `ok` 与 `http_status_code` 两个维度，「被测接口 500」与「环境挂了」
  在数据上无法区分。

### 4.3 生成层（L3）

- 断言质量取决于模型。`evaluate_assertions` 支持 11 个运算符
  （`==` `!=` `>` `>=` `<` `<=` `contains` `not_contains` `exists` `not_exists` `matches`），
  以及 `status_code`、`response_time` 两个特殊路径，但**生成什么断言**没有约束。
- 易变字段（`traceId`、`timestamp`、`nonce`）容易被写成精确断言，导致必然失败。
- 无去重。同一接口生成 20 条几乎一样的用例时，没有任何机制拦截。

### 4.4 对话层（L4）剩余项

见[模式设计](Mode-System-Design.md) §七：服务端授权、人工审批、计划结构化、事件重放。

## 五、阶段计划

顺序由依赖关系决定，不由优先级决定。每个阶段都有可验证的验收条件。

### Phase 1 · 事件与轨迹（前置，规模最小）

目标：让一轮对话可以被完整回放。

- [ ] 新增 `conversation_event` 表（`conversation_id` / `seq` / `type` / `payload` / `created_at`）
- [ ] `stream_answer` 在渲染 SSE 的同时落库事件
- [ ] 前端支持按 `seq` 补齐缺失事件

**验收**：流中途断开后重连，页面能恢复到与实际执行一致的状态。

### Phase 2 · 测试资产（L1）

目标：用例从「文件」变成「可管理的资产」。

- [ ] 新增 `test_case` 表（`space_id` / `endpoint_id` / `name` / `method` / `path` /
      `headers` / `body` / `assertions` / `unique_hash` / `version`）
- [ ] 生成结果先写资产表，`testcases/` 作为导出视图而非真源
- [ ] 按 `unique_hash` 去重（当前生成流程没有读取侧去重）
- [ ] 用例编辑接口与前端列表

**验收**：同一指令生成两次，第二次能识别出与第一次重复的用例，且总数不翻倍。

### Phase 3 · 执行引擎（L2）

目标：确定性地跑一批用例，结果可比较。

- [ ] `run_case()` 纯函数：输入 `CaseSpec` / `EnvSpec`，输出 `CaseResult`，不碰 ORM
- [ ] run 级连接复用
- [ ] 变量系统（`{{token}}` 显式引用，替代模型隐式记忆）
- [ ] 错误分类：`ASSERT_FAILED` / `TRANSPORT_ERROR` / `SERVER_ERROR` / `ENV_ERROR` /
      `SKIPPED` / `CASE_INVALID`，其中 `ENV_ERROR` 必须中止整批
- [ ] 新增 `test_result` 表，`agent_run` 与批量执行共用同一套记录结构

**验收**：同批用例连跑 10 次，结果集合完全一致；并发与串行结果一致。

### Phase 4 · 回归与差异（L2 之上）

- [ ] run 之间 diff：新增失败、已修复、新增用例
- [ ] 报告从「按 `run_id` 实时聚合 HTTP 调用」升级为「按用例维度持久化」
- [ ] 零断言用例一律判 `CASE_INVALID`，不参与通过率

**验收**：能回答「这次比上次多了哪 3 个失败」，且答案可追溯到具体断言。

## 六、三条不可让步的原则

这三条是重构时用真实故障换来的，后续任何阶段都不应违背。

### 6.1 LLM 不进入执行路径

执行引擎的 import 里不允许出现 `llm` / `langchain`。一旦模型参与执行，
用例就不可复现，回归对比（「这次和上次比，哪条挂了」）立刻失去意义。
Agent 可以**生成**用例、可以**触发**执行，但不能**代替**执行。

### 6.2 错误必须分类

当前只有 `ok` 与 `http_status_code`。这个粒度下，「被测接口返回 500」与「测试环境不可达」
在报表上看起来一样，都是失败。前者是缺陷、应当修；后者是环境问题、应当中止并报错。

最危险的情况是把 `ENV_ERROR` 当成普通失败继续跑完，最后产出一个「通过率 92%」的假报告。
**环境不可达时必须中止整批**，不要假装测试完成了。

### 6.3 「通过」必须可信

测试工具最坏的情况不是报错，是报一个假的通过率。以下几种情况都会产出「通过」：

- 断言列表为空 → 全部通过
- 断言路径写错、取不到值 → 取决于比较实现
- 依赖未满足被标 `skipped` → 可能没从分母里排除

**规矩：没有断言的用例不允许标记为 passed。** 一条零断言的「通过」会持续污染通过率指标，
而且比失败更危险——它看起来是好的。

---

## 七、不打算做的事

- **不重建 LangGraph 工作流**。图适合固定拓扑，测试执行的分支由被测系统决定，不值得为它维护一套图。
- **不做 test-as-code 的双向同步**。用例以数据库为真源、文件为导出，不做「文件改了自动回写库」，
  双向同步的冲突处理成本远高于收益。
- **不做内置脚本沙箱**。工具沙箱明确不含 shell 与任意代码执行，
  需要复杂逻辑时应落在执行引擎的变量与断言能力上，而不是让模型写 Python。
